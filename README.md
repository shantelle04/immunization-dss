# Immunization Decision Support System

A web-based decision support system that helps healthcare workers in childhood immunization programmes:

1. **Predictive vaccine inventory analytics:** weekly demand forecasts per vaccine and facility, and stock-out alerts before the next replenishment.
2. **Smart scheduling and defaulter tracking:** a prioritised list of children who have missed doses, and an outreach session plan.
3. **Digital health passport:** a portable immunization record per child (FHIR R4 Immunization), retrievable by any authorised facility.

Stack: React (frontend), Django REST Framework (API), PostgreSQL (database), Python analytics (pandas, statsmodels, scikit-learn, Keras).

All child and facility operations data in this repository is **synthetic**, generated by a seeded simulator calibrated to published national coverage figures. No real patient data is stored or used.

## Repository layout

| Path | Contents |

## Quick start

All commands run from the repository root through one cross-platform runner, `scripts/dev.py`.

| Step | Linux / macOS | Windows (PowerShell) |
|---|---|---|
| 1. Install dependencies (creates `.venv`) | `python3 scripts/dev.py setup` | `py scripts\dev.py setup` |
| 2. Generate `.env` with random secrets | `python3 scripts/dev.py env` | `py scripts\dev.py env` |
| 3. (optional) Review the non-secret settings in `.env` | host, port, names | host, port, names |
| 4. Start PostgreSQL 16 in Docker | `python3 scripts/dev.py db-up` | `py scripts\dev.py db-up` |
| 5. Check Django starts | `python3 scripts/dev.py check` | `py scripts\dev.py check` |
| 6. Run all tests | `python3 scripts/dev.py test` | `py scripts\dev.py test` |

Steps 2 to 6 in one go: `python3 scripts/dev.py bootstrap`. Result-producing commands (`simulate`, `validate`, `eda`, `test`, `lint`, `check`) append a line to a local results ledger when `docs/logs/` exists.

Placeholders are rejected: Django refuses to start, and the database container refuses to initialise, while any secret is missing, too short, or still `changeme`.

## Commands

| Command | What it does |
|---|---|
| `setup` | Create `.venv`, install pinned Python packages (`requirements.txt`) and npm packages (`frontend/package-lock.json`) |
| `env` | Create `.env` from `.env.example` with a random value for every `changeme` entry; owner-only permissions; never overwrites and never prints a value |
| `bootstrap` | First run on a new machine: `env` (if `.env` is missing), `db-up`, `check`, `test` |
| `history` | Render the results ledger as a markdown table |
| `db-up` / `db-down` | Start (and wait until healthy) or stop PostgreSQL 16; data persists in a Docker volume |
| `db-shell` | `psql` inside the container as the application role |
| `db-reset` | Delete the database volume (asks for confirmation); the next `db-up` re-creates the roles from `.env` |
| `check` | Django system check, including the startup settings validation |
| `test [analytics\|backend\|frontend]` | pytest and Jest; default runs all three |
| `lint` | `ruff check` and `ruff format --check` |
| `simulate [--force]` | Generate the seeded synthetic dataset into `data/synthetic/` (about 70 s, one CPU core, about 0.7 GB RAM, low priority). Skipped in about 1 s when a validated run with the same seed, config and generator code exists |
| `validate [run_dir]` | Run the 11 validation checks on a generated run |
| `eda [run_dir]` | Exploratory figures and the dataset description for a validated run |

## Model training (Google Colab only)

Models are never trained on a development machine (D-14): `immdss backtest` and `immdss train-final` refuse to fit SARIMA or the GRU outside Colab. Open `notebooks/immdss_colab_pipeline.ipynb` in Colab (File > Open notebook > GitHub), set the runtime to GPU and run all cells. The notebook regenerates the identical synthetic data from seed 42, checks it against `analytics/configs/evidence_hashes.json`, and runs exploration, the rolling-origin backtest of all four models, the comparison, selection and final training. Details: `docs/12_DATA_TO_TRAINING_PIPELINE.md`.

The database listens on `127.0.0.1:5433` (set `DB_PORT` in `.env` to change it). The application and the test suite connect with separate roles (`DB_USER`, `DB_TEST_USER`), created on first start by `backend/docker/initdb/01-roles.sh`.
